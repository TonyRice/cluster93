# Engine Benchmark Suite (`benchmarks/engines`)

Automated benchmark comparison framework evaluating JavaScript runtime engines (**Javet / V8** vs. **GraalJS**) compiled inside standalone GraalVM `native-image` worker processes (`cluster93-worker`).

---

## 1. Why This Exists & Functional Purpose

Cluster93 provides sandboxed JavaScript execution for multi-tenant serverless workloads and AI agent tooling. Under **D-126** (Engine-Neutral Runtime), we decoupled the host bindings from the underlying JS engine to evaluate alternative engines.

The purpose of this benchmark suite is to empirically measure:
1. **Security & Sandboxing Bounds:** What happens when malicious/untrusted guest code executes resource exhaustion attacks? Does the engine stop them internally at the isolate heap limit, or does it leak uncounted native memory until the OS kernel / cgroup kills the entire worker process?
2. **Execution Throughput & JIT Latency:** Comparing warm iteration speeds across compute, typed arrays, regex, event loop, JSON parsing, and object-heavy JavaScript workloads (including Octane suites like Richards and DeltaBlue).
3. **Cold Start & Tail Latency:** Timing first-script evaluation latency vs. warm iteration latency (JIT compilation overhead and Truffle AST warmup), along with p99 GC pause times.
4. **Memory Footprint & Idle Scalability:** Measuring RSS and private dirty memory per idle isolate service and under heavy memory churn.
5. **GraalVM Editions (Community Edition vs. Oracle GraalVM):** Measuring whether Oracle GraalVM's enterprise JIT compiler (GFTC license) narrows the 2–9× object/JSON performance gap observed in GraalJS Community Edition (CE).

## 2. Directory Structure

```
benchmarks/engines/
├── bin/                   # Compiled worker binaries (worker-javet, worker-graaljs) & build metadata
├── workloads/             # Microbenchmarks & real-world workloads (.js)
│   └── vendor/            # Vendored Octane workloads & stubs (deltablue, richards)
├── results/               # Historical benchmark runs (timestamped directories)
│   └── <timestamp>/
│       ├── machine.json   # Machine hardware profile, power profile & GraalVM edition
│       ├── thermal.csv    # CPU temperature and frequency logged every 5 seconds
│       ├── results.jsonl  # Raw machine-readable benchmark results
│       └── summary.md     # Markdown tables generated by summarize.py
├── build.sh               # Builds native worker binaries under cgroup memory caps
├── run.sh                 # Executes benchmark workloads, hostile attacks, and idle tests
└── summarize.py           # Summarizes results.jsonl into comparative markdown tables
```

From the repo root, `benchmarks/run.sh engines` runs this suite (and `benchmarks/run.sh` lists every
target); the commands below assume you are already in `benchmarks/engines/`.

## 3. Workloads & Attack Suite

### Workload Categories (`workloads/*.js`)
- **JSON & Dynamic Objects:** `json-roundtrip.js`, `service-router.js`, `deltablue.js` (Octane constraint solver), `richards.js` (Octane OS simulation), `sort.js`.
- **Numeric & Compute:** `sha256-js.js`, `crypto-hash.js`.
- **Text & Encoding:** `buffer-codec.js`, `text-codec.js`, `string-build.js`, `regex-tokenize.js`, `url-parse.js`.
- **Event Loop & Streams:** `promise-timers.js`, `events.js` (EventEmitter), `stream-pipeline.js`, `kv-loop.js`, `zlib-roundtrip.js`, `map-set-churn.js`.

### Hostile Memory Attacks (`run.sh § hostile`)
Runs with a 64 MB script limit under a 512 MB kernel cgroup cap to determine what stops the attack:
- `heap-bomb`: Unlimited JavaScript object allocations.
- `buffer-8gb`: Single 8 GB ArrayBuffer allocation.
- `buffers-1gb`: Sixty-four 16 MB ArrayBuffers.
- `resizable-1gb`: Resizable ArrayBuffer expanding to 1 GB.
- `growable-sab-1gb`: Growable SharedArrayBuffer expanding to 1 GB.
- `tolocale-churn`: High-frequency `toLocaleString` allocations churning native ICU memory.
- `intl-held`: Retaining 100,000 `Intl.DateTimeFormat` instances.
- `wasm-1gb`: WebAssembly module growing memory to 1 GB.
- `host-copy-1gb`: Passing 1 GB payload across the host-guest bridge into native crypto.

## 4. How to Run the Benchmarks

### Prerequisites
1. **Linux with cgroup v2** (`systemd-run --user` available).
2. **GraalVM JDK 25+** (either Community Edition or Oracle GraalVM installed via SDKMAN or downloaded).
3. **Machine State:** Keep the machine otherwise idle. Run on balanced power profile with Intel Turbo disabled (`no_turbo=1`) to prevent thermal throttling from skewing comparisons.

### Step 1: Detect & Select GraalVM SDK

`build.sh` automatically checks for GraalVM in the following priority:
1. `GRAALVM_HOME` environment variable
2. `JAVA_HOME` environment variable
3. SDKMAN active candidate (`~/.sdkman/candidates/java/current`)
4. Any installed SDKMAN GraalVM candidate (`~/.sdkman/candidates/java/*graal*`)
5. System `PATH` (`native-image`)

To use a specific SDKMAN version (e.g. Oracle GraalVM):
```bash
# Activate via SDKMAN:
sdk use java 25.4.4+1-graal

# Or manually set GRAALVM_HOME:
export GRAALVM_HOME="$HOME/.sdkman/candidates/java/25.4.4+1-graal"
```

### Step 2: Build the Worker Binaries

Run `build.sh`. Each build runs under a memory cap (default 9 GB) using `systemd-run`:

```bash
cd benchmarks/engines

# Build both workers (default):
./build.sh

# Or build only GraalJS:
ENGINES="graaljs" ./build.sh

# Or build only Javet (V8):
ENGINES="javet" ./build.sh
```

During build, `build.sh` prints the detected GraalVM path, version, and edition (**Oracle GraalVM** vs **GraalVM Community**) and saves `bin/build-metadata.json`.

### Step 3: Run the Benchmarks

Run `run.sh` to execute the full comparison suite:

```bash
cd benchmarks/engines

# Run all engines (takes ~45-60 minutes):
./run.sh

# Or run a targeted engine (e.g., test Oracle GraalJS alone, ~15-20 minutes):
ENGINES="graaljs" ./run.sh

# Or compare Javet against GraalJS:
ENGINES="javet graaljs" ./run.sh
```

#### Optional Tuning Environment Variables:
- `WARMUP_MS` (default: `20000` / 20 s): Warmup duration per workload.
- `WARMUP_MIN` (default: `200`): Minimum warmup iterations before measurement.
- `MEASURED` (default: `50`): Number of measured iterations for computing median and p99.
- `BENCH_HEAP_MB` (default: `512`): Heap limit provided to workers during benchmark runs.
- `CAP` (default: `512M`): Kernel memory cap applied during hostile memory tests.
- `RUN_CAP` (default: `4G`): Kernel memory cap applied during speed benchmarks.

### Step 4: Reviewing Results

Runs are **indicative single-machine numbers**, kept to compare engines on the same hardware on the same
day; they are not a maintained performance claim. Results are placed in
`benchmarks/engines/results/<YYYY-MM-DD-HHMM>/` (git-ignored):
- `summary.md`: Formatted Markdown report comparing start-up, idle memory, warm iteration times, p99 tail latency, cold starts, and hostile test outcomes.
- `results.jsonl`: Raw per-iteration and per-workload metrics.
- `thermal.csv`: CPU clock speed and package temperature history.
- `machine.json`: System hardware specifications, power profile, and recorded GraalVM compiler edition.

To re-generate `summary.md` manually for any previous run:
```bash
python3 summarize.py results/<YYYY-MM-DD-HHMM>/results.jsonl
```
